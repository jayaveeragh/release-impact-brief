# release-impact-brief

> Work in progress. Phases 0–5 done (foundation, Java facts, system structure, LLM interpretation, web app, drill-down and branch map); Phase 6 (chat) next.

Paste a public GitHub URL and get a visual explanation of the repository, from architecture down to the branches inside one endpoint. Describe a bug and get a one-page brief of what a likely fix could affect, to help decide whether the fix goes into a release.

Design rule: **facts first, creativity on top.** Deterministic parsing produces facts with file, line and confidence. An LLM decides how to present them. A validator drops anything the facts don't support.

## Development

Requires Python 3.12+.

```bash
python3 -m venv .venv
.venv/bin/pip install -e ".[dev]"
.venv/bin/ruff check . && .venv/bin/ruff format --check .
.venv/bin/mypy
.venv/bin/pytest              # offline tests
.venv/bin/pytest -m network   # tests that fetch from GitHub
```

## Usage

```bash
.venv/bin/rib fetch https://github.com/spring-projects/spring-petclinic [--ref <branch|tag|sha>]
```

This fetches one pinned commit into a temp folder (nothing from the repo is executed), prints the commit SHA and file counts, then deletes the clone. Repos over 20,000 files or 200 MB are refused; raise `RIB_MAX_FILES` / `RIB_MAX_SIZE_MB` in `.env` for bigger ones (summarising a big repo with a local model takes hours the first time).

```bash
.venv/bin/rib facts https://github.com/spring-projects/spring-petclinic [--kind class|method|field|endpoint|entity|module|config|...]
```

This extracts code facts (each with file and line), the call graph, and build/deployment facts, stores them in `.rib/facts.sqlite` keyed by commit SHA (replacing that commit's previous facts), and lists them.

Edges aren't printed yet; query them directly, for example:

```bash
sqlite3 .rib/facts.sqlite "select kind, confidence, count(*) from edges group by 1, 2;"
```

```bash
.venv/bin/rib structure https://github.com/spring-petclinic/spring-petclinic-microservices
```

This classifies the repo's layout and runtime style, lists the evidence for each verdict (file and line), the services, how they connect (routes, HTTP calls, data stores, messaging, outside systems), and a list of everything it couldn't settle. When signals conflict it says "unclear" and shows both sides.

### LLM settings

By default the LLM work runs on a **free open model on your own machine** through [Ollama](https://ollama.com): install Ollama, then `ollama serve` and `ollama pull qwen3:14b` (about 9 GB; needs roughly 16 GB of memory). Nothing is sent anywhere and nothing is billed; it is slower and less sharp than a hosted model.

Copy `.env.example` to `.env` (gitignored) to change settings. `RIB_MODEL` picks the model: `ollama:<model>` (free, local), a Claude model ID such as `claude-opus-5-5` (paid, needs `ANTHROPIC_API_KEY`), or `fake` (canned answers). For paid models, `RIB_COST_CONTROL=on` (default) estimates each run's cost first and stops at `RIB_SPEND_CAP_USD` (default $1); `off` skips the estimate and the cap. Tests never call a model; `.venv/bin/pytest -m llm` runs the one live test against whatever `RIB_MODEL` is set to.

```bash
.venv/bin/rib summarize https://github.com/spring-projects/spring-petclinic [--estimate-only] [--yes]
```

This writes a summary for each class, each module and the whole repo, using the LLM. With cost control on it first shows how many requests it will make and a cost range, and asks before spending (`--yes` skips the question, `--estimate-only` stops there). Answers are cached in `.rib/facts.sqlite`, so running it again costs nothing; a failed answer is reported and asked again next time. Try it for free with `RIB_MODEL=fake`.

```bash
.venv/bin/rib view https://github.com/spring-petclinic/spring-petclinic-microservices [--yes]
```

This runs the summaries, then asks the LLM how to present the repo and writes a validated view spec to `.rib/views/<owner>__<repo>@<commit>.json`. Every box, step and link in it points at a real fact; anything the LLM invented is removed and listed.

### Web app

```bash
(cd frontend && npm ci && npm run build)   # once, and after UI changes
.venv/bin/rib serve                         # http://127.0.0.1:8765
```

Paste a public GitHub URL and the analysis runs in the background (fetch, facts, summaries, view) with progress on the page; with a paid model and cost control on it shows the estimate and waits for you to confirm. The server only listens on 127.0.0.1 and never sends settings or keys to the browser. For UI work, `npm run dev` in `frontend/` serves the UI with hot reload and forwards `/api` to `rib serve`.
